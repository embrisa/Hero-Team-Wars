# Phase 5E Work Packet - Runtime Logic, Scenarios, and Evidence

Status: HTW-01 through HTW-05 are implemented through deterministic source modules, repeatable model scenarios, and hash-linked static evidence; exact World Editor/Warcraft III runtime acceptance remains gated.

## Goal

Make all HTW logic changeable through source transactions and make gameplay
acceptance repeatable, scenario-driven, and tied to exact transaction/build
hashes.

## Required runtime source modules

The MCP-native JASS package must include deterministic modules for:

- initialization and one-time bootstrap;
- centralized tuning values;
- phase state, timers, current round/wave IDs, and transition guards;
- team/hero mapping, lives, death accounting, revival, elimination, victory,
  and draw;
- deterministic base waves, arena spawn controllers, tracking, cleanup, and
  exact-once resolution;
- personal gold, War Camps, purchases, queues, destination routing, and
  staggered sends;
- public phase/timer/lives display, incoming composition/threat, queue state,
  hero compositions/levels, and `[HTW]` debug events;
- six-team living-order round-robin routing after the two-arena loop passes.

No gameplay module may mutate map structure directly. It consumes the typed
team, region, object, and tuning registries generated by the composer.

## Scenario harness

Add a debug/test profile with deterministic scenarios for:

- fresh initialization;
- preparation -> combat -> resolution;
- single hero death;
- both heroes dead and three-life wipe penalty;
- duplicate/deferred death callback;
- timeout and cleanup;
- elimination and victory/draw;
- personal purchase isolation;
- correct opposing-arena destination and no self-send;
- two-arena repeatability;
- six-team route offset, elimination recalculation, and no carryover.

Each scenario emits structured `[HTW]` markers containing chunk ID, scenario
ID, round, wave ID, team, expected result, and actual result. A visible marker
is runtime evidence only when a user or approved observation recorder confirms
it on the exact build.

## MCP tools and artifacts

Add the following agent-facing tools without bypassing existing transaction
gates:

- `wc3_compose_gameplay_source`: read an approved module manifest and emit a
  source artifact plus hashes; it does not mutate a map;
- `wc3_validate_gameplay_source`: run syntax, symbol, dependency, and profile
  checks against a source manifest;
- `wc3_prepare_gameplay_chunk`: create a reviewed transaction containing the
  generated source and all input hashes;
- `wc3_run_scenario_build`: build a uniquely named debug scenario artifact;
- `wc3_record_chunk_result`: attach chunk, scenario, transaction, build, and
  test-session IDs to observed pass/fail evidence.

Composite tools may call existing services, but must return every underlying
ID and preserve the reviewable diff/validation/build sequence.

## Acceptance tests

- Static-check every authored source file before a map build.
- Run every happy-path scenario twice from a fresh map load.
- Exercise early completion, timeout, duplicate callback, and deferred event
  paths for the current wave ID.
- Confirm failed builds and failed gameplay sessions remain immutable and tied
  to their exact hashes.
- Record editor-open, game-load, smoke, and playtest milestones separately.
- Never upgrade evidence from process start or static validation alone.

## Completion gate

The logic/evidence packet is complete when HTW-01 through HTW-05 can be built
from source manifests, tested with repeatable scenarios, and recorded without
manual source copying. Full HTW-06 remains gated on the six-team map/profile
packet.

## Implementation evidence (2026-08-30)

The packet is implemented through the MCP source and transaction pipeline:

- The manifest at `tools/wc3-map-mcp/scripts/mcp/manifest.json` composes the
  deterministic JASS package, typed runtime variables, trigger declarations,
  dependency order, and the `mvp_2arena` profile. Runtime modules cover
  bootstrap, tuning, state, phases, waves, heroes, lives, elimination,
  routing, economy, purchases, queues, staggered sends, information, cleanup,
  and debug markers.
- `wc3_compose_gameplay_source`, `wc3_validate_gameplay_source`,
  `wc3_prepare_gameplay_chunk`, `wc3_run_scenario_build`, and
  `wc3_record_chunk_result` preserve source, transaction, revision, build,
  scenario, and optional observation-session identifiers. The composed source
  is marked as generated; replacing it directly detaches the generated model
  instead of pairing arbitrary script text with stale gameplay metadata.
- HTW-01 through HTW-05 are exercised by
  `tools/wc3-map-mcp/mcp-server/test/integration/gameplay-phase5e.test.ts`.
  That test creates a fresh reviewed transaction for each chunk, validates the
  revision, builds the assigned scenarios, checks two repeats, verifies the
  structured markers, and records static-only evidence tied to the exact build
  hash. No manual source copying is used.
- The deterministic MVP harness reports 20 scenarios, 20 passed, 0 failed,
  and 2 repeats. It covers fresh initialization, phase transitions, hero
  deaths, the three-life wipe penalty, duplicate/deferred callbacks, timeout,
  cleanup, elimination/victory/draw, personal gold isolation, opposing-arena
  routing, two-arena repeatability, and six-team route/elimination/no-carryover
  model paths.
- Observed automated verification: 60/60 .NET tests passed; 39/39 MCP tests
  passed; the Phase 5E integration test passed; and the published CLI harness
  reported 20/20 scenarios passed with `evidence_level=static_only` and
  `runtime_verified=false`.
- The approved source map was not modified. Its SHA-256 before and after the
  implementation is
  `027AA23AAB7D94EDD8CD09EFBE799DBCFCDC5B2775FF0B36A07CD6BB19CEC834`.

This is source/static acceptance evidence, not Warcraft III runtime evidence.
No editor-open, game-load, smoke-test, or playtest milestone was observed in
this implementation pass, so those gates remain explicitly unclaimed. The
six-team model scenarios validate routing and elimination behavior, but the
checked-in playable map/profile remains the approved four-player,
two-team/two-arena MVP; HTW-06 therefore remains gated on its map/profile
packet.
